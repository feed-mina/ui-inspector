0 · 결론 한 문장

3 · 꼬리 질문 (사용자가 물은 것만)

Q1. 스프링부트나 FastAPI 와 DB 를 따로 쓰면서 SDUI 방식으로 스키마를 만들 수 있나?

용어: 여기서 스키마는 세 가지다. ① 화면 스키마 = manifest 의 pages[].nodes, ② 호출 스키마 = 플러그인 action/hydrator 의 inputSchema/outputSchema(JSON Schema 파일), ③ DB 스키마 = 내 백엔드 몫이며 키트가 관여하지 않는다. [확인]

원리: 키트 설계 문서가 코어의 비목표로 "DB 직접 프로비저닝"과 "앱 고유 비즈니스 로직"을 명시한다(docs/architecture/core-adapter-template-boundary.md). 키트는 화면 JSON 과 호출 계약만 보관하고, 업무 데이터는 내 서버가 갖는다.

우리 코드: ui-inspector 는 지금 프런트 전용이다. 어제 인수인계 문서가 백엔드·DB "미포함"으로 점검해 두었고(docs/ui-inspector-handover.pdf 1쪽), 상태는 URL·JSON 으로만 오간다(src/state.js:32-47, :93-104). 즉 ②와 ③은 새로 만드는 것이지 옮기는 것이 아니다.

권고: 핀 스키마가 이미 src/state.js:49-86 validateState 에 명세로 존재하므로, 그것을 그대로 JSON Schema 4장으로 옮겨 계약을 만들었다. FastAPI 면 Pydantic 모델의 model_json_schema(), 스프링부트면 springdoc 의 /v3/api-docs 가 같은 파일을 만들어 준다. [추측: 권고]

Q2. 핀을 꼭 Studio 요소로 넣어야 한다면 우회로가 있나?

확인된 것: 없다. 요소 종류는 BASE_ELEMENT_REGISTRY 조회로 끝나고 없으면 던진다(src/base-elements.js:58-60). 플러그인의 provides.components 는 manifest 검증을 통과시키는 선언일 뿐, 게시 페이지 렌더러의 요소 표를 늘리지 않는다. [확인]

대안: 핀 레이어 전체를 플러그인이 그린다. 게시 페이지는 노드마다 data-sdui-node 를 남기므로(src/published-page.js:25) 플러그인이 그 앵커를 찾아 자기 오버레이를 붙일 수 있다. 지금 북마클릿이 임의 페이지에 붙는 방식과 같다. [추측: 설계]
